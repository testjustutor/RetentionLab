RetentionLab - Files NOT used in the live pipeline that starts at services/shared/pythonBridge.js
====================================================================================================
Generated by tracing the actual import/call graph, starting from PythonBridge.runFullAudioPipeline(),
which is the ONLY method in pythonBridge.js that spawns a Python process, and it ALWAYS runs exactly
one script:

    pythonBridge.js  --spawn-->  services/engine/engine_main.py
        -> PipelineContext (orchestrator/pipeline_context.py)
        -> PipelineRunner  (orchestrator/pipeline_runner.py)
             -> ExecutionManager (orchestrator/execution_manager.py)
             -> DependencyGraph  (orchestrator/dependency_graph.py)
             -> RuntimeManager   (orchestrator/runtime_manager.py)
             -> TASK_REGISTRY (orchestrator/task_registry.py) dispatches, by feature flag:
                  media          -> task/media_task.py          -> services/media.py
                  transcription  -> task/transcription_task.py  -> services/transcription.py,
                                     services/json_store.py, task/cache_manager.py
                  audit          -> task/audit_task.py          -> engine/audit_service.py (CANONICAL)
                  summary        -> task/summary_task.py        -> services/summary.py, services/file_store.py
                  tutor_eval     -> task/tutor_eval_task.py     -> services/tutor_eval_worker.py
                                     (this is what writes meeting_session_scores)
                  persist_results-> task/persist_results_task.py-> services/transcript_builder.py,
                                     database/python_db.py

No other scriptName is ever passed to PythonBridge.runStage() anywhere in the codebase (checked
server.js, all controllers/routes, test-engine.js, socraticbot.js) - engine_main.py is the single
entry point actually reachable from the bot/recording pipeline.

====================================================================================================
GROUP A - Never imported/executed at all in this flow (fully orphaned / dead files)
====================================================================================================
These are alternate entry points or legacy modules that nothing in the pythonBridge.js -> engine_main.py
chain ever imports, even indirectly. They only reference each other, not the live pipeline.

  services/engine/main.py               - standalone CLI (`python -m services.engine.main`), calls
                                           transcriber.transcribe_and_diarize() directly. Never invoked.
  services/engine/python_main.py        - standalone CLI, calls pipeline.run_pipeline() directly. Never invoked.
  services/engine/runner.js             - Node spawn wrapper for the old AssemblyAI engine. Not required()
                                           anywhere in the codebase.
  services/engine/python_runner.js      - Node spawn wrapper for services.engine.video_convert. Not required()
                                           anywhere in the codebase.
  services/engine/video_convert.py      - only ever invoked via python_runner.js (above), which is itself
                                           unused, so this is unreachable too.
  services/engine/whisperx_engine.py    - only referenced via a LAZY import inside pipeline.py's dead
                                           run_pipeline() function body - never actually executed.
  services/engine/assemblyai_engine.py  - same: lazy import inside pipeline.py's dead code path only.
  services/engine/channel_transcriber.py- same: lazy import inside pipeline.py's dead code path only.
  services/engine/health_check.py       - same: lazy import inside pipeline.py's dead code path only.
  audit_bridge.py (project root)        - older standalone Node<->Python bridge (pre-engine_main.py).
                                           Calls MediaService/TranscriptionService/ai_audit.AuditService
                                           with a method signature (extract_audio/.process()) that no
                                           longer matches the current classes - already broken, and
                                           nothing calls this script anymore.
  services/python_deepgram/*            - a separate Deepgram-based transcription experiment
                                           (__init__.py, main.py, runner.js, transcriber.py). Not wired
                                           into pythonBridge.js or engine_main.py at all.

====================================================================================================
GROUP B - Imported only as a side-effect of package __init__.py, but never actually exercised
====================================================================================================
Python must run services/engine/__init__.py and services/engine/services/__init__.py the first time
ANY submodule under those packages is imported (which engine_main.py does). Both __init__.py files
eagerly import several legacy modules that the real task DAG never calls into. So these files DO get
loaded into memory on every run, but their classes/functions are dead weight - nothing in the actual
pipeline instantiates or calls them.

  services/engine/__init__.py imports (unconditionally, every run):
      services/engine/transcriber.py        - transcribe_and_diarize() never called by the DAG
                                               (the lazy call site in diarization_engine.py._try_assemblyai
                                               is itself unreachable - see note below).
      services/engine/client.py             - AssemblyAIClient never instantiated by the DAG.
      services/engine/config.py             - only used by client.py above (init_sdk / build_transcription_config).
      services/engine/pipeline.py           - run_pipeline() never called by the DAG.
      services/engine/resemblyzer_diarizer.py - ResemblyzerDiarizer never instantiated by the DAG.

  services/engine/pipeline.py itself imports at module level (so these load too, transitively):
      services/engine/whisper_engine.py     - WhisperEngine never used (the DAG uses
                                               services/engine/services/whisper_loader.py +
                                               whisper_runner.py instead, a different implementation).
      services/engine/audio_preprocess.py   - AudioPreprocessor never used by the DAG.
      services/engine/storage_output.py     - save_diarization_result / save_plain_transcript never
                                               called by the DAG.

  services/engine/services/__init__.py imports (unconditionally, every run):
      services/engine/services/ai_audit.py    - explicitly marked in code comments as a
                                                 "legacy/unused duplicate" of audit_service.py.
                                                 Never instantiated by task/audit_task.py.
      services/engine/services/audit_worker.py- same: legacy duplicate scoring implementation,
                                                 explicitly called out as "no longer wired into the
                                                 pipeline" in task/audit_task.py's own comments.

  services/engine/report_schema.py,
  services/engine/report_scorer.py,
  services/engine/report_storage.py       - imported at module level by audit_service.py, but only
                                             used by AuditService.process_audit_report(), which is
                                             called ONLY from the dead pipeline.py (Group A) - never
                                             from task/audit_task.py's run_audit()/process_audit() path
                                             that the live DAG actually uses.

Note: services/engine/services/diarization_engine.py IS imported and its .process() path is reachable
in principle, but transcription_task.py currently calls TranscriptionService.transcribe() only and
never .diarize() (documented in task/persist_results_task.py), so DiarizationEngine, speaker_resolver.py
and the AssemblyAI fallback path inside it are effectively idle in the current DAG even though they are
not "dead" the way Group A/B files are - wiring up diarization later would activate them without
touching any of this code.

====================================================================================================
Scope note
====================================================================================================
This list covers only what is reachable/unreachable from pythonBridge.js's single call path
(engine_main.py). Some "unused here" files (e.g. services/engine/services/ai_audit.py,
audit_bridge.py) may still be wired into OTHER entry points in this codebase (admin controllers,
routes/session_scores.py, controllers/python/python_session_scores_controller.py, etc.) that were
not part of this trace - this report does not claim those files are unused project-wide, only that
the bot-recording pipeline that runs through pythonBridge.js never touches them.
